## 2. ⚠️ 계약에 관해 확인할 것 — `scarcity` 정의

> 확인할 것이 하나 더 있습니다 — **`weight` 문턱으로는 필수/우대가 갈리지 않습니다(3-⑮).**
> 직무 24개 중 5개가 통째로 빕니다. 두 건 다 같이 보시는 편이 낫습니다.

계약은 이렇게 정의합니다.

```
scarcity = log(전체 직무 수 / 이 스킬이 있는 직무 수)
spread   = 스킬이 등장하는 직무 분포의 엔트로피
```

**이 둘은 같은 사실을 두 번 재는 것입니다.** 등장 직무가 많으면 엔트로피가 크고(`spread`↑),
동시에 IDF 는 작아집니다(`scarcity`↓). 정의상 역상관이 필연입니다.

실제 데이터로 계산한 결과입니다.

| 방식 | spread ↔ scarcity 상관 | 사분면 |
|---|---|---|
| **계약 정의 (IDF)** | **r = −0.958** | lockin 85 · common 100 · noise 14 · **leverage 1** |
| 우대/요건 비율 | r = −0.219 | noise 40 · lockin 59 · common 59 · **leverage 42** |

**계약대로 계산하면 `leverage`(피벗 무기)가 하나도 안 나옵니다.** 두 축이 한 직선 위에 놓여
2×2 가 대각선 두 칸으로 무너집니다. 이 제품의 핵심 메시지가 "당신의 피벗 무기는 이것"인데
그 사분면이 비어 버립니다.

### 대안 — `reqFreq` / `prefFreq`

공고는 스킬을 두 칸에 나눠 적습니다.

```
자격요건 (Requirements)  이 정도는 다들 갖고 있어야 함   → 흔하다
우대사항 (Nice to have)  드물어서, 있으면 좋음          → 희소하다
```

**"드물어서 있으면 좋은 것"을 채용담당자가 우대에 적습니다.** 추정이 아니라 문서에 적힌 구분입니다.

```
scarcity = prefFreq / (reqFreq + prefFreq)
```

두 값을 `job-skills.json` 에 넣어뒀으니 **어느 쪽으로 계산할지 앱이 고르면 됩니다.**
`docs/skill-map.html` 상단 토글로 두 방식을 나란히 볼 수 있습니다.

> ⚠️ 이것도 완벽하지 않습니다. **실제 보유자 비율이 아니라 수요 쪽에서 뽑은 대리지표**입니다.
> 공급 데이터(공개 이력서 등)로 검증하는 것이 다음 단계입니다.

### ⑤ ✅ 수정됨 — 부분문자열 매칭으로 `weight` 가 부풀려졌던 문제

**2026-09-02 발견, 같은 날 수정.** 기록으로 남깁니다.

**고친 방법** — `build_roles.py` 의 매칭을 단어 경계 정규식으로 바꿨습니다.

```python
re.compile(r"(?<![A-Za-z0-9가-힣])" + re.escape(name) + r"(?![A-Za-z0-9])")
```

- **앞**은 영문·숫자·**한글**을 모두 막습니다 — `빅데이터 분석` 안의 `데이터 분석`을 세지 않기 위해서입니다
- **뒤**는 영문·숫자만 막습니다 — 한글 조사(`분석을`·`개발이`)가 붙는 것은 정상 등장입니다
- **대소문자를 구분**합니다. `re.I` 를 쓰면 사전을 만들 때의 대문자 비율 판단이 무효가 됩니다
  (소문자 `sass` 가 `Sass` 로 20건 오탐)
- 매칭은 소문자 키가 아니라 **정규 표기**(`Sass`·`AWS`)로 합니다

**결과** — 매핑 777 → 516건. **261건(34%)이 오탐이었습니다.**

주니어 표기가 4%뿐이라 따로 떼면 표본이 무너집니다.

### ⑫ ✅ 수정됨 — 한글 별칭도 같은 문제가 있었습니다

⑤의 부분문자열 문제를 고칠 때 **오른쪽 경계를 영문·숫자만 막았습니다.** 한글은 열어 뒀는데,
`파이썬을 다룬다` 처럼 조사가 붙기 때문입니다. 그 틈으로 합성어가 들어왔습니다.

| 잘못 잡힌 것 | 실제 문장 |
|---|---|
| `Java` (별칭 "자바") | "**자바**스크립트가 웹이라는 한계를 벗어나" |
| `hwp` (별칭 "한글") | "이재원님의 **한글** 자막을 참고해주세요" |
| `Linux` (별칭 "리눅스") | "**리눅스**마스터" — 자격증 이름 |

고친 규칙은 **오른쪽 한글은 조사·어미만 허용**입니다.
세 파일이 각자 같은 정규식을 적어 두고 있어 한 곳을 고치면 어긋나므로,
`collect_common.word_pattern()` 한 곳으로 모았습니다. 앞으로 경계를 바꿀 일이 있으면 거기만 고치면 됩니다.

**별칭 자체가 틀린 것도 6개 걷어냈습니다.** 경계 규칙으로 막을 수 없는, 뜻이 다른 별칭입니다.

| 뺀 별칭 | 코퍼스에서 실제로 뜻한 것 |
|---|---|
| `한글` → hwp | 공고는 "hwp(한글) 파일"이라 `hwp` 로 이미 잡힘 |
| `생성형 AI` → AI 코딩 도구 | "생성형 AI 기반 CS 운영 효율화" — 기술 범주이지 코딩 도구가 아님 |
| `파이프라인 구축` → 시스템 구축 | 13건 전부 "CI/CD 파이프라인 구축"·"데이터 파이프라인 구축" |
| `서비스 운영` → 시스템 운영 | 18건이 "고객 서비스 운영 지원" — 고객 응대 |
| `뷰` → Vue | 2건이 "그래프 뷰"·"모바일 웹 뷰" |
| `노드` → Node.js | "지도 데이터는 방대한 노드와 경로로" |

`데이터 파이프라인`(→ETL) · `쿼리`(→SQL) · `사용자 경험`(→UX/UI) 은 **용례를 읽어 보고 남겼습니다.**
코퍼스에서 실제로 그 뜻으로 쓰였습니다.

이 수정만 놓고 보면 영향은 매핑 1건으로 작습니다. 작다고 두면 다음에 더 나쁜 형태로 돌아옵니다.

### ⑬ 직무 해설 글 73건을 따로 모아 대조했습니다

**⚠️ 무게를 섞지 않았습니다.** 블로그는 개인 의견이고 공고는 실제 수요입니다.

### ⑭ ✅ 수정됨 — 전이성(`spread`)을 5% 문턱이 걸린 표로 재고 있었습니다

**2026-09-02 발견, 같은 날 수정.** 검증 화면에서 스킬이 전부 왼쪽(전이성 0 부근)에 눌어붙어 있어 찾았습니다.

`_roles.json` 의 `required_skills` 는 **그 직무 공고의 5% 이상에 나온 스킬만** 담습니다.
"이 직무가 요구하는가"를 정하는 기준으로는 맞습니다. 그런데 그 표로 전이성을 재면,
**여러 직무에서 3%씩 쓰이는 스킬이 어디에서도 안 잡혀** 「직무 1개짜리」가 되고 엔트로피가 0 이 됩니다.

| | 직무 1개에만 걸림 | `spread` 중앙값 | `spread` ≥ 0.5 |
|---|---|---|---|
| 5% 문턱을 건 표 (틀림) | **43%** | 0.186 | 38개 |
| 문턱 없이 등장 수로 셈 (맞음) | **5%** | 0.531 | 101개 |

바뀐 예입니다.

```
PyTorch    2 →  9개 직무    spread 0.129 → 0.581
Jira       5 → 11개 직무    spread 0.511 → 0.753
SAP        2 →  7개 직무    spread 0.186 → 0.657
Java      11 → 14개 직무    spread 0.575 → 0.619
```

`build_roles.py` 가 문턱 없는 직무별 등장 수(`skill_job_dist`)를 따로 내보내고,
`spread` 와 `scarcity` 는 **그것으로만** 계산합니다.
`weight` 는 영향을 받지 않습니다 — 그것은 원래 "이 직무가 요구하는가"의 값이라 문턱이 맞습니다.

**⚠️ 남아 있는 약점 — 표본이 적으면 엔트로피가 전이성을 부풀립니다.**
`Elastic` 은 5개 직무에 **1건씩** 나와 `spread` 0.597 이 됩니다. `Python`(341건, 0.871)과 같은 눈금에 놓입니다.
`spread ≥ 0.5` 인 101개 중 **13개가 총 10건 미만**입니다.
지금은 고치지 않고 **드러냈습니다** — 화면에 「표본 10건 이상만」 필터와 건수 표기를 넣었고,
`payload` 의 `n` 필드로 확인할 수 있습니다. 축 자체를 축소 보정할지는 앱 쪽과 같이 정하는 편이 낫습니다.
### ⑮ ⚠️ 계약에 관해 확인할 것 — `weight` 문턱으로는 필수/우대가 안 갈립니다

[`DATA_SPEC.md`](DATA_SPEC.md) 는 `weight ≥ 0.6` → 필수, `0.3~0.6` → 우대로 가르라고 합니다.
그런데 `weight` 는 **"이 직무 공고 몇 건에 나왔나"**이지 **"필수인가"**가 아닙니다.

```
매핑 575건의 weight 분포
  ≥ 0.6        25건            ← 필수로 잡히는 것
  0.3 ~ 0.6    45건            ← 우대
  < 0.3       505건 (88%)      ← 화면에서 통째로 사라진다
```

| 직무 | 표본 | 최고 `weight` | 계약 문턱 결과 |
|---|---|---|---|
| 소프트웨어 엔지니어 | 280 | Python **0.35** | 필수 0 · 우대 1 |
| 프로덕트 매니저 | 117 | UX/UI **0.18** | 필수 0 · 우대 0 |
| 프로젝트·프로그램 매니저 | 36 | SQL **0.22** | 필수 0 · 우대 0 |
| 마케팅·그로스 | 15 | SEO **0.27** | 필수 0 · 우대 0 |

**직무 24개 중 5개는 필수·우대가 둘 다 비어 추천이 아예 안 나옵니다.**
공고 제목이 넓은 직무일수록 심합니다 — "소프트웨어 엔지니어" 안에 여러 스택이 섞여 있어
어느 한 스킬도 과반에 못 미칩니다. 표본을 더 모아도 이 성질은 바뀌지 않습니다.

### 대안 — 공고가 이미 나눠 적어 둔 것을 쓴다

자격요건 절과 우대사항 절은 **채용담당자가 직접 가른 것**입니다. 추정이 아닙니다.

```
requirement = 자격요건 절 등장 > 우대사항 절 등장  →  required
              그 반대                              →  preferred
              등장 3건 미만                         →  판정 보류(null)
```

같은 데이터로 필수·우대가 빈 직무는 **24개 중 1개**(표본 5건짜리 모션 디자이너)뿐입니다.

| 직무 | 필수 (자격요건 절 등장 건수) |
|---|---|
| 소프트웨어 엔지니어 | Python(72) · Java(40) · AWS(39) · TypeScript(37) |
| 백엔드 개발자 | Java(62) · AWS(45) · Spring(42) · Python(33) |
| 프로덕트 디자이너 | UX/UI(25) · Figma(13) · HCI(7) |
| 디자이너(일반) | Photoshop(20) · Illustrator(15) · Figma(13) |
| 데이터 엔지니어 | SQL(23) · Python(20) · AWS(14) · ELT(10) |

`weight` 는 계약대로 그대로 두고 `requirement` · `reqShare` 를 **옆에 더했습니다.**
앱이 어느 쪽을 쓸지 정하면 됩니다. 「⚠️ 2. `scarcity` 정의」와 같은 성격의 확인 사항입니다.
### ⑯ ✅ 수정됨 — 전이성 축의 오른쪽 15%가 구조적으로 비어 있었습니다

⑭를 고친 뒤에도 지도의 오른쪽이 허전했습니다. 눈으로 보고 찾았습니다.

엔트로피를 `ln(직무 수)` 로 나누고 있었습니다. **스킬이 24개 직무에 균등하게 퍼졌을 때**의 값입니다.
그런데 직무 표본이 280건~5건으로 제각각이라 그런 분포는 만들어질 수가 없습니다.
모든 직무에서 똑같은 비율로 쓰이는 스킬조차 **직무 규모 분포**를 따를 뿐입니다.

```
ln(직무 수)              = 3.1781      ← 나누고 있던 값
직무 규모 분포의 엔트로피     = 2.6955      ← 실제로 도달 가능한 최대
                                       → 축 오른쪽 15% 는 아무도 못 간다
```

**도달 가능한 상한으로 나눕니다.** `spread = 1.0` 의 뜻이 생깁니다 —
"모든 직무에서 그 직무 규모에 비례해 쓰인다", 곧 가장 전이성이 높은 상태입니다.

```
SQL     0.917      AI 코딩 도구  0.874        ← 어디서나 쓰인다
Python  0.871      Java        0.619
CISA    0.000      ISMS-P      0.000        ← 보안 직무에만
```

상관계수는 바뀌지 않습니다(축을 상수배 한 것이라 `r`은 그대로입니다).
사분면 개수는 바뀝니다. 지금 데이터에서 1.0 을 넘어 잘린 항목은 **0개**입니다.

**왜 놓쳤나** — 값 자체는 그럴듯했고(0.45 중앙값) 검증 스크립트도 통과합니다.
**지도를 그려 놓고 보기 전까지는 드러나지 않는 종류**였습니다. 축을 그리는 화면이 있어서 잡았습니다.

```
ALIAS   코퍼스에 없지만 이력서에 나올 표기   (파이썬 · 쿠버네티스 …)
MERGE   코퍼스에 실제로 있어 흡수할 표기     (MySQL → SQL …)
```

넷 다 ALIAS 에만 적혀 있었습니다. 그런데 코퍼스에 그 표기가 **실제로 있어서** 별도 스킬로 남았습니다.
MERGE 로 옮겨 흡수했습니다 — 스킬 233 → 229개, 매핑 580 → 575건.

`validate-data.mjs` 는 이름이 다르면 통과시킵니다(`Vue` ≠ `Vue.js`).
그래서 `export_contract.py` 가 **내보내기 직전에 막습니다** —
어떤 별칭이 다른 스킬의 이름이면 그 자리에서 실패하고 어느 쌍인지 알려줍니다.

### 어휘를 어떻게 걸렀나

스킬 이름을 골라내는 데 **세 겹**이 필요했습니다. 어느 하나도 나머지를 대신하지 못했습니다.

| 층 | 묻는 것 | 걸러지는 것 |
|---|---|---|
| ① 허용 목록 (7,044) | 그런 이름의 기술이 존재하나 | `IMPORTANT` · `NOTICE` · `OTE` · `KDN` |
| ② 대문자 사용 비율 ≥ 0.7 | 이 코퍼스에서 고유명사로 쓰이나 | `be`(9%) · `build`(25%) · `help`(11%) |
| ③ 관용구·회사명 차단 | 공고에서만 쓰는 말인가 | `Basic` · `Fluent` · `PTO` · `DoorDash` |

②가 특히 중요했습니다. Linguist 에 `BE`·`Make`·`Just` 라는 언어가, simple-icons 에 `Now`·`Here` 라는
서비스가 실재해서 **평범한 영어 문장의 be·build·make 가 전부 스킬로 잡혔습니다**(762건짜리 `be` 가 최상위).
목록은 "그런 기술이 있나"를 답하고 대문자 비율은 "이 문장에서 그 뜻으로 썼나"를 답합니다. 다른 질문입니다.

### 표기 통합

계약이 가장 강조한 항목입니다. 14묶음 30개를 흡수했습니다.

```
SQL      ← MySQL · PostgreSQL · TiDB · RDBMS · DBMS
UX/UI    ← UX · UI
LLM      ← LLMs · GenAI
시스템 개발 ← 정보시스템 개발 · 전산개발 · 전산지원 개발
```

여기에 **이력서에 나올 표기**를 더했습니다 — `파이썬`·`쿠버네티스`·`리액트`·`k8s`·`포토샵` 등.
코퍼스 관찰만으로는 안 되는 부분이라 사람이 판단해 적었습니다(`scripts/collect/synonyms.py`).

**별칭은 넣기보다 빼기가 어렵습니다.** 뜻이 조금 넓은 별칭 하나가 수십 건을 오염시킵니다.
6개를 걷어낸 근거는 3-⑫에 있습니다. 별칭을 추가할 때는 코퍼스에서 **실제 용례 몇 줄을 읽고** 넣어 주세요.

### 갱신하는 법

```bash
python scripts/collect/collect_publicjobs.py    # 공공기관 (증분 · 최근 12개월만)
python scripts/collect/collect_ats.py          # Greenhouse · Lever · Ashby 보드
python scripts/collect/collect_remote_boards.py # Arbeitnow · Jobicy · RemoteOK · Remotive
python scripts/collect/build_corpus.py          # 코퍼스 (자격요건/우대사항 분리)
python scripts/collect/build_allowlist.py       # 허용 목록
python scripts/collect/mine_vocab.py            # 어휘 채굴 + 좌표
python scripts/collect/build_roles.py           # 직무 역할
python scripts/collect/collect_guides.py        # 직무 해설 글 (robots.txt 확인 후)
python scripts/collect/verify_guides.py         # 해설 글 교차검증 → verified.json
python scripts/collect/export_contract.py       # → data/*.json (등급 병합 포함)
python scripts/collect/build_interim.py         # → 앱용 data/interim/*.json (업무 역량·목업 보정 포함)
python scripts/collect/build_skill_map.py       # 검증 화면 docs/skill-map.html 갱신
```

앱용 `interim`에는 [`data/demo-curation.json`](../data/demo-curation.json)을 적용합니다.
원본 계약 데이터와 수집 근거는 바꾸지 않고, O*NET의 직업별 소프트웨어 목록처럼 목업 추천을 오염시키는 행만
제외합니다. 또한 도구 빈도에 밀려 역할 구분에 필요한 업무 역량이 필수 목록에서 빠지는 경우에는
`pinPairs`로 고정합니다. 보정 대상과 이유는 코드가 아니라 이 설정 파일에 남겨 재생성해도 같은 결과가
나오게 합니다.

API 키는 저장소 밖 `.env` 에서 읽습니다. **어느 파일에도 키를 적지 않습니다.**

### 원본은 커밋하지 않습니다

수집 원본 85MB 는 `data/raw/` 에 있고 `.gitignore` 로 제외됩니다.
**집계 결과(스킬명·숫자)는 사실이라 저작권 대상이 아니지만, 공고 원문은 타사 저작물입니다.**
`docs/data/collection-manifest.jsonl` 에 출처 URL·수집일시·해시만 남겨 재현 가능하게 했습니다.
