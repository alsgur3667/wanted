## 1. MVP 스코프 — 이것만 만든다

### ✅ IN (핵심 루프 하나)

```
① 이력서 붙여넣기 (또는 샘플 프로필 원클릭)
        ↓  LLM
② Skill DNA 추출  — bullet을 (행동/대상/도구/성과)로 원자화
        ↓  사전계산 임베딩 + 룰
③ 성장 자산 지도  — 전이성 2×2 (레버리지 / 락인 / 커먼 / 노이즈)
        ↓
④ 다음 커리어 3선 — 몰랐던 인접 직무 + 적합도 + 부족 역량
        ↓
⑤ 공유 카드 생성  — 이미지 1장 다운로드/공유  ← 투표 20% 장치
```

### ❌ OUT (전부 자른다)

| 자르는 것 | 대체 |
|---|---|
| 회원가입 / 로그인 | 세션 기반, DB 없음 |
| 실시간 채용공고 크롤링 | JD 200~300건 **사전 스냅샷** + 임베딩 사전계산해 JSON 번들 |
| LightGBM 학습 | 라벨 데이터 없음 → **룰 + LLM 스코어링**. "데이터 확보 시 GBM 전환"은 로드맵으로 |
| 이력서 파일 업로드(PDF 파싱) | 텍스트 붙여넣기만. 여유 생기면 추가 |
| 마이페이지 / 히스토리 | 없음 |
| 다국어 | 한국어만 |

## 2. ★ 절대 빠뜨리면 안 되는 것: 샘플 프로필

**심사위원과 투표자는 자기 이력서를 넣지 않는다.**
입력창만 덩그러니 있으면 서비스를 아예 안 보고 넘어간다. 이게 예선 탈락의 가장 흔한 원인.

→ **원클릭 샘플 프로필 3종**을 첫 화면에 배치:
- 마케터 5년차 → PM 전환 희망
- 개발자 3년차 → AI 엔지니어 전환 희망
- 비IT 직군(예: 간호사/교육) → 직무 대전환

샘플은 **결과를 사전 캐싱**해두면 응답 즉시 + API 비용 0.

## 3.5. 2인 협업 규칙 — 여기서 프로젝트가 살거나 죽는다

둘 다 바이브코딩이면 역할 분담보다 **충돌 방지**가 훨씬 중요하다.
AI 에이전트는 파일을 통째로 재작성하는 일이 잦아서, 같은 파일을 두 명이 건드리면 머지에 며칠이 날아간다.

### 철칙 4개

**① 같은 파일을 동시에 수정하지 않는다 — 파일 소유권을 나눈다**

| | **A (팀장)** — 파이프라인 축 | **B** — 표현 축 |
|---|---|---|
| 담당 | 입력 → LLM 추출 → 스코어링 → 결과 JSON | 결과 JSON → 화면 |
| 소유 파일 | `app/api/**`, `lib/**`, `data/**`, 프롬프트 | `app/page.tsx`, `components/**`, 스타일 |
| 산출물 | `AnalysisResult` JSON을 뱉는 API | 랜딩, 2×2 지도, 커리어 카드, 공유 이미지, 모바일 |

**② 인터페이스를 Day 1에 고정한다 (생명줄)**

`types.ts` 하나를 두 사람의 **계약서**로 삼는다. 이 파일만은 반드시 합의 후 수정.

```ts
// types.ts — 두 사람 사이의 계약. 변경은 반드시 합의 후.
export type Quadrant = 'leverage' | 'lockin' | 'common' | 'noise';

export interface Skill {
  name: string;
  quadrant: Quadrant;
  spread: number;      // 0~1  가로축
  scarcity: number;    // 0~1  세로축
  evidence: string;    // 근거가 된 이력서 문장 (설명가능성)
}

export interface NextCareer {
  jobTitle: string;
  fitScore: number;        // 0~100
  surpriseScore: number;   // 높을수록 '몰랐던' 직무
  bridgeSkills: string[];  // 이미 가진 무기
  gapSkills: string[];     // 채워야 할 것
  reason: string;          // 한 문장 설명
}

export interface AnalysisResult {
  skills: Skill[];
  nextCareers: NextCareer[];   // 3개
  summary: string;
}
```

**③ Mock 먼저 — B는 A를 기다리지 않는다**

`data/mock-result.json`에 `AnalysisResult` 샘플을 Day 1에 만들어 둔다.
B는 처음부터 끝까지 mock으로 UI를 완성하고, 마지막에 실제 API로 스위치만 한다.

**④ 매일 짧게 싱크 + 자주 푸시**

- 각자 브랜치 → 하루 최소 1회 머지 (오래 묵히면 충돌 폭탄)
- Vercel Preview Deploy로 서로 확인
- 매일 15분: "오늘 뭐 만졌고, 내일 어디 만질 건지" — 파일 충돌 사전 차단이 목적

## 6. AI 도구 활용 기재문 (필수 항목) — 작성 방향

단순 나열(❌ "Claude 사용")이 아니라 **역할 분담**으로 쓴다.

```
[설계 파트너] Claude — 전이성 지수 수식 설계, 스킬 온톨로지 구조 검토
[구현 파트너] Claude Code / Cursor — Next.js 컴포넌트, API 라우트 구현
[제품 내부]   Claude API — 이력서 bullet 원자화 (action/object/tool/metric 추출)
[검증]        LLM 교차검증 — 추출 결과를 다른 프롬프트로 재검증해 오류율 측정
```

> 김호민 대표(SparkClaw)의 평가 기준이 *"AI를 팀원처럼 설계하고 활용한 경험"* —
> 팀 **규모**가 아니라 **AI를 어떻게 팀에 편입시켰는가**를 본다.
> 프레임: **"사람 2명 + AI 팀원 3역(설계·구현·검증)으로 운영한 5인 팀"**

### 함께 기록해두면 좋은 것
개발 과정에서 **AI에게 시켰다가 틀린 사례와 그걸 어떻게 잡았는지**를 메모해둘 것.
크래프톤 Cofa-Probe가 평가하는 항목이 정확히 *문제정의 → AI활용 → 반복개선 → 결과검증* 과정이다.
"AI가 이걸 틀렸고, 우리가 이렇게 검증해서 고쳤다"는 사례 2~3개가 조정석 심사위원에게 가장 강한 증거가 된다.
