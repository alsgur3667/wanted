스킬 지도

채용공고 2,012건(최근 12개월)에서 캐낸 스킬 …개와 직무 …개. 여기에 직무 해설 글 73건을 따로 모아 교차검증한 결과를 얹었습니다. docs/DATA_SPEC.md 계약 형식으로 변환한 결과를 눈으로 확인하는 화면입니다.

축 계산 방식에 따라 지도가 완전히 달라집니다

계약은 scarcity = log(전체 직무수 / 이 스킬이 있는 직무수) 로 정의합니다. 그런데 이는 IDF 이고, spread(직무 분포 엔트로피)와 같은 사실을 두 번 재는 것입니다. 등장 직무가 많으면 엔트로피가 크고 동시에 IDF 는 작아집니다.

실측 상관이 … 입니다. 두 축이 한 직선 위에 놓여 피벗 무기 사분면이 …개가 됩니다. 아래 토글로 직접 비교해 보세요.

제안하는 대안은 공고의 자격요건 / 우대사항 구분을 쓰는 것입니다. "드물어서 있으면 좋은 것"을 채용담당자가 우대에 적습니다 — 추정이 아니라 문서에 적힌 구분입니다. 같은 데이터로 …, 사분면 넷이 모두 채워집니다(피벗 무기 …개).

이 숫자들은 scripts/collect/build_skill_map.py 가 데이터에서 다시 재어 넣습니다. 가로축은 두 방식이 같습니다 — 계약이 정의한 spread(직무 분포의 엔트로피)입니다. 1.0 은 “모든 직무에 그 직무 규모에 비례해 등장” 입니다. ln(직무 수)로 나누면 어떤 스킬도 0.85 를 넘을 수 없어 축 오른쪽 15%가 빕니다(문서 3-⑯).

weight 문턱으로 필수/우대를 가르면 직무 5개가 통째로 빕니다

계약은 weight ≥ 0.6 → 필수, 0.3~0.6 → 우대로 가릅니다. 그런데 weight 는 “공고 몇 건에 나왔나”이지 “필수인가”가 아닙니다. 실측하면 매핑 580건 중 510건(88%)이 0.3 미만입니다 — 소프트웨어 엔지니어의 최고값이 Python 0.35, 프로덕트 매니저는 UX/UI 0.18 입니다. 직무 24개 중 5개는 필수·우대가 둘 다 비어 추천이 아예 안 나옵니다.

공고는 이미 자격요건 절과 우대사항 절에 나눠 적어 두었습니다. 그것을 세면 됩니다. 같은 데이터로 빈 직무가 1개(표본 5건짜리)로 줄고, 소프트웨어 엔지니어 필수는 Python(72) · Java(40) · AWS(39) 가 됩니다. 아래 「직무별 요구 스킬」은 이 방식으로 표시하고, 괄호에 계약 문턱 결과를 같이 적었습니다. job-skills.json 의 requirement · reqShare 필드입니다.
