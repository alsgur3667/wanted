# 로드맵

현재 구현된 범위와, 그 위에 무엇을 얹을 수 있는지.
각 항목은 **"지금 구조에서 무엇만 추가하면 되는가"** 를 함께 적는다.
붙일 자리가 이미 있다는 것이 확장 가능성의 근거다.

현재 화면·API·점수·저장 범위의 기준은 [기능 명세](./FUNCTIONAL_SPEC.md)에서 관리한다.

---

## 현재 (v1)

```
개인   이력서 텍스트 입력  →  역량 추출  →  갈 수 있는 경로 3개
기업   공고 직접·AI 작성   →  인재풀 추천 / 기존 공고 지원자 관리
```

두 화면은 같은 직무·스킬 ID와 역량 커버율 규칙을 공유하고, 입력 방향에 맞는 함수를 호출한다.

```
lib/employer-index.ts   scoreEmployerCandidate(posting, candidate)
                        matchEmployerCandidate(posting, candidate, application)
lib/posting-ai.ts       generatePostingDraft(input)
lib/scoring.ts          buildAnalysis(extractedProfile)
             └ 공통 기반: lib/skill-index.ts (직무 × 스킬 매트릭스)
```

기업 목업에는 회사 18개·공고 48개·지원자 72명·지원 이력 288건이 연결되어 있습니다. 공고를 직접 작성하거나
AI로 문구 초안을 만들고, 새 공고는 지원자가 아닌 가상 인재풀 추천으로 확인할 수 있습니다. 후보 상세 근거와
기존 공고의 전형 상태 변경까지 확인할 수 있지만 모두 가상 데이터이며, 초안과 상태는 서버에 저장하지 않습니다.

**현재 제약** — 실제 지원자 파일을 받는 경로, 채용 계정, 영속 저장소와 개인정보 처리 절차가 없습니다.

## 다음 단계 (v2) — 이력서 파일 일괄 분석

### 무엇을

채용 담당자가 지원자 이력서 파일을 **한 번에 올리면**, 파싱·역량 추출·적합도 산출까지 자동으로 처리해 정렬된 목록을 만든다.

```
이력서 파일 N개 (PDF · DOCX)
      ↓  텍스트 추출
      ↓  LLM 역량 추출        ← 이미 구현됨 (lib/llm.ts)
      ↓  온톨로지 정규화       ← 이미 구현됨 (resolveSkill)
      ↓  적합도 계산          ← 이미 구현됨 (lib/employer-index.ts)
정렬된 지원자 목록 + 직무 전환 후보 표시
```

### 이미 준비된 부분

| 단계 | 상태 |
|---|---|
| 역량 추출 프롬프트 | ✅ 구현 (`lib/prompts/extract.ts`) |
| 표기 정규화 (별칭 매칭) | ✅ 구현 (`resolveSkill`) |
| 적합도·부족역량·온보딩 계산 | ✅ 구현 (`lib/employer-index.ts`) |
| 지원자·지원 이력 데이터 구조 | ✅ 정의됨 (`EmployerCandidate`·`CandidateApplication`) |
| **파일 파싱** | ❌ 미구현 |
| **배치 처리 · 진행률** | ❌ 미구현 |

`matchEmployerCandidate(posting, candidate, application)`은 ID 기반 계약만 받습니다.
실제 파일 파싱 결과를 같은 지원자 계약으로 정규화하면 회사·공고 화면을 유지한 채 입력 계층을 교체할 수 있습니다.

### 왜 이번 범위에 넣지 않았는가

**① 비용이 사용량에 비례한다**
이력서 1건마다 LLM 호출이 발생한다. 개인 화면은 한 사람이 한 번 쓰지만, **기업 화면은 한 번에 수십~수백 건**이 들어온다. 공개된 데모에서 누구나 100개 파일을 올릴 수 있는 상태로 두면 비용이 통제되지 않는다.

**② 심사 기간의 안정성이 우선이다**
LLM 호출이 몰리면 무료 티어 한도에 걸려 서비스가 응답하지 못할 수 있다. 현재는 샘플 프로필 결과를 사전 캐싱해 **핵심 흐름은 LLM 호출 없이 동작**하도록 만들었다.

**③ 개인정보 처리 범위가 달라진다**
타인의 이력서를 업로드받는 순간 수집·보관·파기 정책이 필요하다. 현재는 입력을 저장하지 않는 것으로 단순화했다.

### 실제 도입 시 필요한 것

```
· 파일 파싱      PDF/DOCX → 텍스트
· 배치 큐        건별 병렬 처리 + 진행률 표시
· 비용 제어      조직별 한도, 중복 이력서 해시 캐싱
· 개인정보       업로드 동의, 보관 기간, 파기 절차
```

## v3 — 원티드 데이터 연동

현재 역량 매트릭스는 공개 채용공고 1,100건에서 산출했다. 원티드의 데이터가 연결되면 두 가지가 가능해진다.

### ① 전이 경로 검증
원티드 이력서의 경력 이력에서 **실제 직무 전환 그래프**를 만들 수 있다.
현재는 "역량이 겹치므로 갈 수 있다"까지만 말하지만, 그러면 **"실제로 이 경로로 이동한 사람이 N명 있다"** 까지 말할 수 있다.

> 공개 데이터(KLIPS)로 같은 시도를 했으나 대상 전환자가 17명이라 기각했다.
> 표본 부족이 원인이었으므로, 대규모 이력서 데이터에서는 성립한다.

### ② 성공률 예측
합격보상금 지급 로그는 **입사 후 일정 기간 재직해야 지급**된다.
즉 "서류 합격"이 아니라 **"실제로 붙어서 정착했는가"** 를 검증하는 신호다.

```
label = 입사 확정 + 6개월 재직   (보상금 지급 로그로 검증)
feature = 역량 커버율 · 산업 연속성 · 전이 Lift · 시장 수급
model = LightGBM
```

이 설계는 [`wanted_pivot_simulator_schema.sql`](./wanted_pivot_simulator_schema.sql) 에 스키마 수준으로 정리되어 있다.

**현재 기각한 이유** — 라벨 데이터에 접근할 수 없다. 학습 없이 룰 기반으로 대체하고, 데이터 확보 시 전환하는 것을 전제로 설계했다.

## v4 — 자기개선 루프

```
추천 → 사용자가 실제로 이동 → 결과 관측 → 매트릭스·모델 갱신
```

지금은 추천이 한 방향으로 끝난다. 결과가 다시 들어오면 **쓸수록 정확해지는 구조**가 된다.

| 신호 | 얻는 것 |
|---|---|
| 사용자의 경로 선택 (클릭·저장) | 추천 순위 보정 |
| 재방문 시 역량 변화 | 학습 경로가 실제로 이어졌는지 |
| 입사·정착 결과 | 성공률 모델의 라벨 |

첫 단계로 결과 화면에 **피드백 입력**을 두면, 이후 어떤 신호를 모아야 하는지가 정해진다.

## v5 — B2B 리스킬링 진단

같은 엔진을 조직 단위로 돌리면 **사내 인력의 역량 분포**를 볼 수 있다.

```
개인   내 역량   → 갈 수 있는 직무
기업   요구 역량 → 맞는 사람
조직   구성원 역량 분포 → 부족한 직무 · 사내 이동 후보
```

채용으로 메울지 내부 이동으로 메울지 판단하는 근거가 된다. 계산 로직은 동일하고, 입력이 지원자에서 재직자로 바뀔 뿐이다.

## 우선순위

| | 선행 조건 | 난이도 |
|---|---|---|
| **v2** 이력서 일괄 분석 | 비용 제어 · 개인정보 정책 | 중 |
| **v3** 원티드 데이터 연동 | 데이터 접근 권한 | 상 |
| **v4** 자기개선 루프 | 사용자 기반 | 중 |
| **v5** B2B 리스킬링 | v2 완료 | 중 |

v2가 나머지의 입구다. 파일 입력이 열리면 v4의 피드백도, v5의 조직 단위 분석도 같은 경로를 쓴다.
