# 로드맵

현재 구현된 범위와, 그 위에 무엇을 얹을 수 있는지.
각 항목은 **"지금 구조에서 무엇만 추가하면 되는가"** 를 함께 적는다.
붙일 자리가 이미 있다는 것이 확장 가능성의 근거다.

현재 화면·API·점수·저장 범위의 기준은 [기능 명세](./FUNCTIONAL_SPEC.md)에서 관리한다.
추천 품질의 현재 수준과 남은 결함은 [RESUME_EVAL](./RESUME_EVAL.md)에서 관리한다.

---

## 현재 (v1)

```
랜딩   개인 / 기업 분기  →  데모 로그인 (인증 아님)

개인   이력서 텍스트 입력 또는 파일(PDF·DOCX·TXT)
         →  역량 추출  →  갈 수 있는 경로 3개 · 부족 역량 · 첫 단계

기업   공고 직접·AI 작성  →  인재풀 추천 / 기존 공고 지원자 관리
```

두 화면은 같은 직무·스킬 ID와 역량 커버율 규칙을 공유하고, 입력 방향에 맞는 함수를 호출한다.

```
lib/employer-index.ts   scoreEmployerCandidate(posting, candidate)
                        matchEmployerCandidate(posting, candidate, application)
lib/posting-ai.ts       generatePostingDraft(input)
lib/scoring.ts          buildAnalysis(extractedProfile)
lib/resume-file.ts      extractResumeText(file)     ← 브라우저 파싱
             └ 공통 기반: lib/skill-index.ts (직무 × 스킬 매트릭스)
```

기업 목업에는 회사 18개·공고 48개·지원자 72명·지원 이력 288건이 연결되어 있다. 공고를 직접 작성하거나 AI로 문구 초안을 만들고, 새 공고는 지원자가 아닌 가상 인재풀 추천으로 확인한다. 후보 상세 근거와 전형 상태 변경까지 볼 수 있지만 모두 가상 데이터이며, 초안과 상태는 서버에 저장하지 않는다.

**현재 제약** — 채용 계정, 영속 저장소, 개인정보 처리 절차가 없다. 파일 입력은 **개인 화면 1건 단위**만 열려 있고, 기업 화면의 일괄 처리 경로는 없다.

## 지난 범위에서 바뀐 것

로드맵을 처음 적었을 때와 달라진 지점이다. **v2의 절반이 이미 열렸다.**

| | 그때 | 지금 |
|---|---|---|
| 이력서 파일 파싱 | ❌ 미구현 | ✅ **구현** — `lib/resume-file.ts` (PDF·DOCX·TXT) |
| 공고 AI 초안 | 계획 | ✅ **구현** — `api/employer/posting-draft` (일일 상한 80) |
| 추천 품질 측정 | 채점기 숫자만 | ✅ **이력서 평가 테스트 12건** — 키 없이 재현 가능 |
| 분석 공고 수 | 1,100건 | **1,435건** |
| 진입 흐름 | 단일 페이지 | 랜딩 분기 + 데모 로그인 |

파일 파싱은 **브라우저에서** 돈다. 파일이 서버로 올라가지 않고, 뽑힌 글자를 사용자가 확인한 뒤 분석을 누른다. 같은 라이브러리(`pdfjs-dist`·`mammoth`)는 Node에서도 돌기 때문에, 일괄 처리를 붙일 때는 이 함수를 서버로 옮기면 된다 — 다시 만들 필요가 없다.

## 다음 단계 (v2) — 이력서 파일 일괄 분석

### 무엇을

채용 담당자가 지원자 이력서 파일을 **한 번에 올리면**, 파싱·역량 추출·적합도 산출까지 자동으로 처리해 정렬된 목록을 만든다.

```
이력서 파일 N개 (PDF · DOCX)
      ↓  텍스트 추출          ← 이미 구현됨 (lib/resume-file.ts, 서버 이식 필요)
      ↓  LLM 역량 추출        ← 이미 구현됨 (lib/llm.ts)
      ↓  온톨로지 정규화       ← 이미 구현됨 (resolveSkill)
      ↓  적합도 계산          ← 이미 구현됨 (lib/employer-index.ts)
정렬된 지원자 목록 + 직무 전환 후보 표시
```

### 이미 준비된 부분

| 단계 | 상태 |
|---|---|
| 파일 → 텍스트 추출 | ✅ 구현 (`lib/resume-file.ts` · 브라우저) |
| 역량 추출 프롬프트 | ✅ 구현 (`lib/prompts/extract.ts`) |
| 표기 정규화 (별칭 매칭) | ✅ 구현 (`resolveSkill`) |
| 적합도·부족역량·온보딩 계산 | ✅ 구현 (`lib/employer-index.ts`) |
| 지원자·지원 이력 데이터 구조 | ✅ 정의됨 (`EmployerCandidate`·`CandidateApplication`) |
| **파싱 함수의 서버 이식** | ❌ 미구현 |
| **배치 큐 · 진행률** | ❌ 미구현 |

`matchEmployerCandidate(posting, candidate, application)`은 ID 기반 계약만 받는다.
파일 파싱 결과를 같은 지원자 계약으로 정규화하면 회사·공고 화면을 유지한 채 입력 계층만 교체할 수 있다.

### 왜 이번 범위에 넣지 않았는가

**① 비용이 사용량에 비례한다**
이력서 1건마다 LLM 호출이 발생한다. 개인 화면은 한 사람이 한 번 쓰지만, **기업 화면은 한 번에 수십~수백 건**이 들어온다. 공개된 데모에서 누구나 100개 파일을 올릴 수 있는 상태로 두면 비용이 통제되지 않는다.

**② 심사 기간의 안정성이 우선이다**
LLM 호출이 몰리면 무료 티어 한도에 걸려 서비스가 응답하지 못할 수 있다. 현재는 샘플 프로필 결과를 사전 캐싱해 **핵심 흐름은 LLM 호출 없이 동작**한다.

**③ 개인정보 처리 범위가 달라진다**
타인의 이력서를 업로드받는 순간 수집·보관·파기 정책이 필요하다. 현재 개인 화면은 파일을 브라우저 밖으로 내보내지 않는 것으로 이 문제를 아예 피했다. 기업 일괄 처리는 같은 방법을 쓸 수 없다.

### 실제 도입 시 필요한 것

```
· 서버 파싱      lib/resume-file.ts 를 Node 경로로 이식
· 배치 큐        건별 병렬 처리 + 진행률 표시
· 비용 제어      조직별 한도, 중복 이력서 해시 캐싱
· 개인정보       업로드 동의, 보관 기간, 파기 절차
```

## v3 — 원티드 데이터 연동

현재 역량 매트릭스는 공개 채용공고 **1,435건**에서 산출했다. 원티드의 데이터가 연결되면 세 가지가 가능해진다.

### ① 지금 남은 결함이 데이터로 풀린다

[RESUME_EVAL](./RESUME_EVAL.md)의 "아직 남은 것" 중 **절반이 표본 부족**이다.

| 남은 결함 | 원인 |
|---|---|
| **사무 직군 자체가 없다** | 수집 공고에 총무·인사·재무·영업관리가 거의 없음 |
| 임베디드 직무 정의가 약하다 | 공고 표본 **11건** |
| 마케팅·그로스 필수 상위 3개가 수기 입력 | 공고 표본 **19건** |
| 모바일 개발자가 누구나 필수 100% | 요구 목록이 3개뿐이라 변별이 안 됨 |

알고리즘을 고쳐서 풀 문제가 아니라 **표본이 늘면 사라지는** 문제다. 그래서 기각이 아니라 대기다.

#### 사무 직군을 먼저 넣는다

현재 24개 직무의 직군 분포는 개발 15 · 기획 5 · 디자인 4이고, 공고의 73%가 개발이다.
사무직 경력을 넣으면 갈 수 있는 곳이 기획 계열로 좁아지고, 그마저 표본이 얇아
`우선순위 관리`·`이해관계자 조율` 같은 **범용 역량이 순위를 정한다.**

> 점수식은 이미 필수 역량에 3배 가중을 둔다. 그런데 어떤 직무를 갖다 대도 필수 커버율이
> 다 같이 낮으면 3배를 줘도 변별이 되지 않고, 그때 남은 범용 역량이 순위를 만든다.
> **계산식을 고쳐서 풀리는 문제가 아니다** — 추천할 직무가 목록에 없기 때문이다.

그래서 v3의 첫 작업은 모델이 아니라 **사무 직군 공고 수집**이다. 직무를 추가하고
요구 역량을 세는 경로는 이미 있으므로(`scripts/collect`), 데이터가 들어오면
`data/jobs.json`에 직무를 늘리고 매트릭스를 다시 만드는 것으로 끝난다.

### ② 전이 경로 검증

원티드 이력서의 경력 이력에서 **실제 직무 전환 그래프**를 만들 수 있다.
현재는 "역량이 겹치므로 갈 수 있다"까지만 말하지만, 그러면 **"실제로 이 경로로 이동한 사람이 N명 있다"** 까지 말할 수 있다.

> 공개 데이터(KLIPS)로 같은 시도를 했으나 대상 전환자가 17명이라 기각했다.
> 표본 부족이 원인이었으므로, 대규모 이력서 데이터에서는 성립한다.

### ③ 성공률 예측

합격보상금 지급 로그는 **입사 후 일정 기간 재직해야 지급**된다.
즉 "서류 합격"이 아니라 **"실제로 붙어서 정착했는가"** 를 검증하는 신호다.

```
label   = 입사 확정 + 6개월 재직   (보상금 지급 로그로 검증)
feature = 역량 커버율 · 산업 연속성 · 전이 Lift · 시장 수급
model   = LightGBM
```

이 설계는 [`wanted_pivot_simulator_schema.sql`](./wanted_pivot_simulator_schema.sql) 에 스키마 수준으로 정리되어 있다.

**현재 기각한 이유** — 라벨 데이터에 접근할 수 없다. 학습 없이 룰 기반으로 대체하고, 데이터 확보 시 전환하는 것을 전제로 설계했다. 점수 계산이 코드로 되어 있어 **모델로 바꿔 끼우는 자리가 한 곳**이다.

## v4 — 자기개선 루프

```
추천 → 사용자가 실제로 이동 → 결과 관측 → 매트릭스·모델 갱신
```

지금은 추천이 한 방향으로 끝난다. 결과가 다시 들어오면 **쓸수록 정확해지는 구조**가 된다.

| 신호 | 얻는 것 |
|---|---|
| 사용자의 경로 선택 (클릭·저장) | 추천 순위 보정 |
| 재방문 시 역량 변화 | 학습 경로가 실제로 이어졌는지 |
| 입사·정착 결과 | 성공률 모델의 라벨 |

첫 단계로 결과 화면에 **피드백 입력**을 두면, 이후 어떤 신호를 모아야 하는지가 정해진다.

측정 틀은 이미 있다 — `npm run eval:resumes` 가 키 없이 재현 가능한 기준선을 만든다. 새 신호로 매트릭스를 갱신했을 때 **좋아졌는지 나빠졌는지 판정할 자리**가 이미 준비되어 있다는 뜻이다.

## v5 — B2B 리스킬링 진단

같은 엔진을 조직 단위로 돌리면 **사내 인력의 역량 분포**를 볼 수 있다.

```
개인   내 역량              → 갈 수 있는 직무
기업   요구 역량            → 맞는 사람
조직   구성원 역량 분포     → 부족한 직무 · 사내 이동 후보
```

채용으로 메울지 내부 이동으로 메울지 판단하는 근거가 된다. 계산 로직은 동일하고, 입력이 지원자에서 재직자로 바뀔 뿐이다.

## 우선순위

| | 선행 조건 | 남은 작업 | 난이도 |
|---|---|---|---|
| **v3-a** 사무 직군 추가 | 국내·사무 직군 공고 확보 | 직무 추가 후 매트릭스 재생성 | 하 |
| **v2** 이력서 일괄 분석 | 비용 제어 · 개인정보 정책 | 파싱 서버 이식 + 배치 큐 | 중 |
| **v3-b** 원티드 데이터 연동 | 데이터 접근 권한 | 라벨 확보 후 모델 교체 | 상 |
| **v4** 자기개선 루프 | 사용자 기반 | 피드백 입력부터 | 중 |
| **v5** B2B 리스킬링 | v2 완료 | 입력 계층만 교체 | 중 |

v2가 나머지의 입구다. 파일 입력이 열리면 v4의 피드백도, v5의 조직 단위 분석도 같은 경로를 쓴다.
그 v2의 첫 관문이던 파일 파싱은 **이미 만들어 두었다.** 남은 것은 그것을 서버로 옮기고 줄 세우는 일이다.
