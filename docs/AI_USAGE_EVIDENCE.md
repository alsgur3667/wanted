## 3. 이번 실행 기록

- 실행일: 2026-09-14, 로컬 Windows 환경.
- 확인 코드: `6b38a53`, 문서 작성 전 작업 트리 변경 없음.
- 명령: `npm run eval:resumes`.
- 외부 모델 호출: 없음. `mockExtract` 기반.
- 종료 코드: `0`.
- Vitest: 파일 1개, 테스트 1개 통과. 내부 사례 12건.
- 평가 요약: `1위 적중 11/11 · 연차 적중 12/12 · 금지 직무가 1위 0건`.

주요 출력: iOS 사례는 모바일 개발자(97) → 임베디드·펌웨어(60) → 프론트엔드 개발자(42), 경력 108개월입니다. 기간형 경력 사례는 실행일 기준 103개월이며 기대값 102±6개월을 충족했습니다. 인용 공고 함정 사례는 1위 정답 평가를 하지 않고 금지 직무와 경력 기준을 확인합니다.

이 목록은 실행 결과를 옮긴 요약이며 전체 원본 콘솔 로그 파일을 별도로 보관한 것은 아닙니다. 재현할 때는 명령의 출력을 함께 보관하고 커밋·데이터·실행일을 기록하십시오. 테스트 내부의 현재 날짜 의존성 때문에 모든 출력이 날짜와 무관하게 고정되지는 않습니다.

이번 작업에서는 전체 `verify`, 조사 데이터 평가, 실제 Gemini·Anthropic 호출, 공고 초안의 사람 평가, 브라우저 E2E를 실행하지 않았습니다. 이를 통과한 것으로 표시하지 않습니다.

## 4. 개발 AI 활용 이력과 증거 수준

작업 대화에서 사용자 이력서의 낮은 적합도 조사와 수정, 타 직군 이력서 테스트, 가상 데이터 정제, 기업용 공고 입력 및 AI 초안 기능, 기능 명세와 브랜딩 문서 작성 요청을 확인했습니다. 또한 사용자가 팀원 UI를 기준으로 적용 범위를 정하고, 서비스 방향을 양면 플랫폼으로 변경하고, 커밋·푸시·stash 시점을 결정했습니다.

이것은 사용자 제공 작업 대화에 근거한 활용 이력입니다. 대화 전체의 별도 원본 파일과 모든 프롬프트·응답은 이 저장소에 첨부하지 않았습니다. 따라서 모델별 호출 횟수, 작업별 AI 기여율, 절약 시간·비용 등은 수치로 제시하지 않습니다. 팀원이 작업한 UI까지 이 기록의 AI 결과물로 귀속하지 않습니다.

## 5. 브랜딩 자료와 이미지의 보관 상태

작성 시점에 다음 stash를 읽기 전용으로 확인했습니다.

```text
stash@{0}: On design/brand-system: wip: 양면 플랫폼 브랜딩 문서와 UI 예시 임시 보관
```

현재 작업 트리에 없는 아래 자료는 링크 가능한 현행 파일이 아니라 **stash 보관 자료**입니다.

- 문서: `docs/BRAND_UI_STRATEGY.md`, `docs/DESIGN_AI_HANDOFF.md`, `docs/BRAND_UI_IMPROVEMENT.md`.
- 실제 화면 캡처: `docs/assets/brand-ui/current-main-landing-desktop.png`, `current-main-landing-mobile.png`.
- 생성 참고 시안: 같은 폴더의 `two-sided-landing-desktop-v1.png`, `two-sided-landing-mobile-v1.png`, `personal-result-desktop-v1.png`, `employer-workspace-desktop-v1.png`.

실제 화면 캡처와 AI 생성 시안을 구분해야 합니다. 시안은 구현 결과·사용자 평가 결과가 아니며, 임의 문구나 수치가 들어갈 수 있습니다. 해당 자료를 제출에 첨부하려면 사용자의 UI 작업이 끝난 뒤 복구·검토 여부를 확인해야 합니다. 이번 작업에서는 복구하지 않았습니다.

읽기 전용 확인 예시:

```powershell
git stash list
git show 'stash@{0}^3:docs/BRAND_UI_IMPROVEMENT.md'
```

`stash@{0}` 번호는 새 stash가 만들어지면 달라질 수 있습니다. 사용 전 목록과 제목을 다시 확인하십시오.

## 6. 제출 전 보완하면 좋은 근거

- 실제 LLM 평가: 비식별 입력, 기대 역량, 모델·공급자·실행일, 실제 출력, 누락·오탐과 원문 근거 판단.
- 공고 생성 평가: 입력 조건 유지, 사실 없는 문구 생성 여부, 수정이 필요한 항목과 사용자 승인 여부.
- 독립 이력서 평가: 결함 수정에 사용하지 않은 사례와 직군별 표본, 점수의 적절성에 대한 별도 판단 기준.
- 화면 근거: 현행 UI 캡처와 생성 시안을 분리하여 첨부.
- 기여 확인: 팀원별 AI 활용 내역은 당사자 확인 후 추가.

API 키, 인증 정보, 비식별 처리하지 않은 실제 이력서는 문서와 로그에 포함하지 마십시오.
